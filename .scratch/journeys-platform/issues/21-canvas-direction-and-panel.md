# 21: Canvas direction and a slidable panel

Status: in-progress
Blocked by: 16, 19
Owner: Atlas orchestrator (Claude Fable 5.1), session of Paul Macfarlane, claimed 2026-09-21
Parent: `.scratch/journeys-platform/spec.md`
Priority: between 19 and 17 in the graph tidy-up series (Paul, 2026-09-21): 18 → 16 → 19 → 21 → 17. It must precede 17 because stored positions belong to one direction.

**Scope change:** the graph document gains a Journey-level `layoutDirection` field (`"TB" | "LR"`, default `"TB"`, zod default so every stored document parses). Record a `[SCOPE CHANGE]` on the spec's document contract as part of this ticket. Positions are still never stored here (that is 17).

**Decisions (Paul, 2026-09-21):** the direction is a property of the Journey, not of the Author, so Members share one view and can switch it back and forth freely; it lives in the Draft document and autosaves like every other edit (last write wins). Publishing copies it with the document; nothing reads it at run time. Hiding and showing the panel is a way of reading, not content: it is remembered per browser, never stored on the Journey.

**What to build:**

- **Direction.** `layoutGraph` takes the document's `layoutDirection` as dagre's `rankdir`. In `LR` the boxes' target anchor is on the left and the per-Choice source anchors are spread along the right, ordered by the target box's y (centre) instead of x; the connect dot sits at the bottom-right corner in both; the box toolbar sits above the box in both. `mapOrder` stays top-to-bottom then left-to-right (the reading order of the map as drawn). A two-way control on the canvas beside "Add step" ("Top to bottom" / "Left to right", `role="radiogroup"` or a single toggle button naming the direction it switches to) writes the field through the same edit path as everything else and the map re-lays out; fit-to-all runs on a direction change. When 17 has landed and the Draft holds hand-placed positions, switching direction asks with 17's Auto-arrange confirmation and clears every position, since an arrangement made for one axis is not an arrangement for the other; until 17 lands there is nothing to clear.
- **Slidable panel.** A "Hide panel" button at the top of the Step panel slides it out (the canvas takes the full width and fits view); a "Show panel" button at the canvas's right edge slides it back. Opening a Step from anywhere (a box, an arrow, a problem entry, "Leads here from", "Open", Find step) shows the panel if it is hidden, so the editing gesture never changes; Escape with the canvas focused hides it. The choice is remembered in `localStorage` per browser, defaulting to shown; a hidden panel never blocks autosave or the Delete key.
- **Layout below the canvas.** With 19's step list gone, the Outcomes editor stays beneath the canvas at full width.

Acceptance criteria:

- [ ] Seam A: `layoutGraph` with `layoutDirection: "LR"` places every Choice's target box strictly to the right of its source box (x greater) for a tree document, and with `"TB"` strictly below (y greater); `sourceAnchors` in `LR` are ordered by target y; `mapOrder` is unchanged in shape; a document without the field parses as `"TB"`.
- [ ] Switching the direction on case-3 re-lays the map with no overlaps and every box inside the viewport after the automatic fit; the `draft` row read back holds `layoutDirection: "LR"`; a reload shows left-to-right; switching back restores top-down.
- [ ] Hiding the panel widens the canvas (its frame's width grows) and fits the map; clicking a box shows the panel with that Step; the hidden state survives a reload; Escape hides it again.
- [ ] Every existing canvas spec passes in both directions for the tests that build a branch (parameterise `canvas-add-next-step` and `canvas-connect-and-retarget-by-dragging` over the two directions, or add one left-to-right build test), so dragging to connect works with anchors on the sides.
- [ ] Seam B: build a three-Step branch left-to-right with the panel hidden and shown as needed, publish, walk it in the runner. Screenshots of both directions and a recording under `test-results/`.

Verification and evidence follow `docs/agents/testing.md`: cite the exact commands run; commit any artifact used as PASS evidence under `test-results/`; never include participant Responses or real run data. Use `CONTEXT.md` vocabulary. Spec: `.scratch/journeys-platform/spec.md`. Origin: Paul's design discussion after ticket 16, 2026-09-21.

**Resolved technical decisions (execution, not contract changes):**

- **Schema (D1).** `src/lib/graph/document.ts`: `export const layoutDirectionSchema = z.enum(["TB", "LR"])`, `export type LayoutDirection`, and `layoutDirection: layoutDirectionSchema.default("TB")` in `graphDocumentSchemaWith` (so the strict and the loose envelope share it). `createDraftDocument` writes `layoutDirection: "TB"`. The output type makes the field required, so every literal `GraphDocument` in `src/lib/graph/*.test.ts`, `src/lib/graph/fixtures/large-journey.ts`, and `e2e/setup/documents.ts` gains `layoutDirection: "TB"` (`pnpm typecheck` names each site); the committed seed documents under `scripts/seed/journey-stories/` are untouched — they are parsed, and the default fills them. Doc comment on the envelope: the direction is the Journey's, shared by its Members, autosaved with every edit, copied into a Published Version, read by nothing at run time.
- **Edit path (D1).** `setLayoutDirection(document, direction): GraphDocument` in `src/lib/graph/edit.ts`, returning the same object when nothing changes (as the other edits do) and otherwise a copy with the field set. Seam A cases in `edit.test.ts` (changes it; identity when unchanged; the rest of the document untouched).
- **Layout (D1).** `layoutGraph` passes `document.layoutDirection` as dagre's `rankdir`. `GraphLayout` gains `direction: LayoutDirection` so the canvas draws anchors from the layout it was handed rather than re-reading the document. `sourceAnchors` order a Step's Choices by the target box's centre along the cross axis — x in `TB` (as now), y in `LR` — ties by Choice order. `mapOrder` is unchanged: top to bottom, then left to right, in both directions. The module doc comment and `CanvasNode.sourceAnchors`'s comment say so. Seam A in `layout.test.ts`: on a tree document (the generated 60-Step tree, or a smaller one), `LR` places every Choice's target box's x strictly greater than its source box's x and `TB` every target's y strictly greater than its source's y; `sourceAnchors` in `LR` are ordered by target centre y on a document skewed so the targets land at distinct y (mirror the existing x case); `mapOrder` in `LR` still returns every Step id once, no placeholder, sorted by y then x; determinism holds per direction. In `document.test.ts`: a document without the field parses with `layoutDirection: "TB"`, `"LR"` round-trips, and another value is refused.
- **Direction on the map (D2).** Node and edge data carry the layout's `direction`. The target handle every arrow ends at is renamed from `"top"` to `"in"` everywhere it is named (both node types, `targetHandle`, comments; no spec reads it) and sits at `Position.Top` in `TB`, `Position.Left` in `LR`; the invisible drop handle is unchanged. Source anchors: `Position.Bottom` spread by `left: %` in `TB`; `Position.Right` spread by `top: %` in `LR` (`handleOffset(index, count)` replaces `handleLeft`). The connect dot's centre sits on the box's bottom-right corner in both: `Position.Bottom` with the current style in `TB`; `Position.Right` with `top: "auto", bottom: 12` and the same size and `translate(50%, 50%)` in `LR`. The box toolbar stays `Position.Top` and the peek `Position.Bottom` in both. `selfLoopRoute` takes the direction: in `LR`, out of the anchor to the right by `LOOP_CLEARANCE`, down to `LOOP_SIDE_CLEARANCE` below the box's bottom (`targetY + NODE_HEIGHT / 2 + LOOP_SIDE_CLEARANCE`, the target handle being at the vertical middle of the left edge), left to `LOOP_CLEARANCE` before the target handle's x, up to the target's y, and in — the mirror of the `TB` route, and under dagre's `nodesep` the same way. `layout.ts` is not touched by D2.
- **Direction control (D2).** In the canvas's top-left `Panel`, beside "Add step": a `role="radiogroup"` with `aria-label="Layout direction"` holding two `Button`s with `role="radio"`, `aria-checked`, and roving `tabIndex` (the checked one 0, the other −1; ArrowLeft/Right/Up/Down move and check), labelled "Top to bottom" and "Left to right", the checked one visibly set apart (`bg-accent`). Clicking calls `onSetLayoutDirection(direction)`; the editor applies `setLayoutDirection(documentRef.current, direction)` through `applyEdit`, so it autosaves like every edit. The canvas fits to all when `layout.direction` changes (an effect keyed on it, skipping the first render, `fitView({ duration: 200 })`).
- **Slidable panel (D3).** `DraftEditor` holds `panelShown` (initial `true`, so the server render and the hydrating render agree); an effect on mount reads `localStorage` key `journeys:step-panel` (the value `"hidden"` hides), and hiding or showing writes `"hidden"`/`"shown"`, every access in `try`/`catch`. `selectStep` shows the panel, so every opening — a box, an arrow, a problem entry, "Leads here from", "Open", "Find step", "Add step", "Add next step", "Duplicate" — shows it; the server-side Validation list's `setSelectedStepId(stepId)` button becomes `selectStep(stepId)` so it does too. The grid wrapper transitions its columns (`transition-[grid-template-columns] duration-200 motion-reduce:transition-none`): shown `lg:grid-cols-[minmax(0,1fr)_minmax(0,24rem)]`, hidden `lg:grid-cols-[minmax(0,1fr)_0fr]` with the panel column `min-w-0 overflow-hidden` and `StepPanel` not rendered while hidden (nothing hidden is focusable or read; the `Step` region is simply absent). "Hide panel" is a `Button` (`variant="ghost" size="sm"`) at the top of `StepPanel`, right-aligned above the title field, prop `onHidePanel`. "Show panel" is rendered by `JourneyCanvas` while the panel is hidden, inside the Canvas `section` (made `relative`), `absolute right-2 top-1/2 -translate-y-1/2 z-10`, `variant="outline" size="sm"`, prop `onShowPanel`. Escape on the section itself (`event.target === event.currentTarget`) calls `onHidePanel` — Escape on a box lands on the section (ticket 19), a second Escape hides the panel. Fit after a toggle: the editor bumps a `fitRequest` counter when the panel is hidden or shown and again on the grid's `onTransitionEnd` for `grid-template-columns`; the canvas, on a change of `fitRequest` (not the initial 0), runs `fitView({ duration: 200 })` inside `requestAnimationFrame`, so the fit lands on the final width whether or not the transition ran. Autosave and the Delete key are untouched by any of this: neither runs through the panel.
