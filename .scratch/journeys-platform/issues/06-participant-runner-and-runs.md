# 06: Participant runner and Runs

Status: ready-for-human

Parent: `.scratch/journeys-platform/spec.md`

**What to build:** An anonymous Participant opens `/j/{slug}`, sees a start screen with the Journey's title and description, begins, reads Steps with Choices as buttons, can go back, reaches an Ending, and can start over. The Run is recorded and pinned to the live Published Version at start. Mobile-first, themed later (ticket 11).

Each step has its own URL under the journey so the browser back button works; an in-app Back control does the same. Run id is an unguessable random id in a cookie scoped to the journey slug (it is the only write credential for the Run); refresh resumes at the current step; a step URL with no Run cookie for that journey redirects to `/j/{slug}`. Path semantics (unambiguous because published graphs have no cycles): choosing appends; navigating to a step already in the path truncates to it and increments the backtrack counter; navigating to a step not in the path redirects to the current step; reaching an Ending sets ended-at and outcome id; going back from an Ending clears them. Runs store version id, path, backtrack count, started/ended, outcome id, and a pseudonymous participant id never linked to an account. Unpublished slug → "unavailable" page; unknown slug → 404. Start over creates a new Run.

- **Schema, migration 0005 (additive only).** New table `run`: `id` text primary key (`crypto.randomUUID()` default — this id is the Run's only write credential, so it must be unguessable), `version_id` text not null → `published_version.id` on delete cascade (a Run belongs to the version it is pinned to; the version names the Journey, so there is no `journey_id` column, and deleting a Journey cascades its versions and their Runs), `participant_id` text not null (the pseudonymous cookie id, never linked to an account), `path` jsonb not null typed `string[]` (the current linear route from the Start), `backtrack_count` integer not null default 0, `started_at` timestamptz not null default now, `ended_at` timestamptz null, `outcome_id` text null (an Outcome id inside the version's document, not a foreign key); index on `version_id` for the per-version analytics ticket 10 will run. Generated with `pnpm db:generate` and applied locally with `pnpm db:migrate`. Nothing deployed reads the table, so a build that goes live before the migration keeps working and the migration keeps working under the old code. The `Response` table is ticket 12's.
- **Pure path reducer** `src/lib/graph/run.ts` (no `server-only`; never mutates its inputs): `RunState = { path: string[]; backtrackCount: number; endedAt: Date | null; outcomeId: string | null }`; `currentStepId(state)` (the last of `path`); `startRun(document, now)` → `{ path: [startStepId], backtrackCount: 0, ... }`, and when the Start is itself an Ending, `endedAt: now` and its `outcomeId`; `navigateTo(document, state, stepId, now)` → `{ kind: "stay" } | { kind: "moved"; state } | { kind: "refused"; currentStepId }` with these rules, in order: a `stepId` that is not an own property of `document.steps` is refused; `stepId` equal to the current step is `stay`; `stepId` already in `path` truncates the path to it (inclusive), increments `backtrackCount`, and clears `endedAt` and `outcomeId` (a backtrack — browser back, the in-app Back control, or a typed URL); otherwise the **latest** step in `path` holding a Choice whose `targetStepId` is `stepId` is found — if it is the current step the target is appended; if it is an earlier step the path is truncated to it, `backtrackCount` is incremented, and the target is appended (the participant went back through a cached page the server never saw and chose from there; published graphs have no cycles, so this is never ambiguous); if no step in `path` offers the target, refused. Whenever a move lands on an Ending, `endedAt = now` and `outcomeId` = the Ending's; landing anywhere else leaves both null. Seam A `run.test.ts` over a small hand-written document (Start → two Choices; one branch two deep) covering every rule above: start; start on a single-Ending document ends at once; choosing appends; reaching an Ending sets `endedAt` and `outcomeId`; navigating to the current step stays; back to an earlier step truncates, increments, and clears the Ending; choosing from an earlier path step truncates, increments, and appends; an unknown step, and a real step no path step offers, are refused with the current step named; a refusal leaves the state unchanged; inputs are never mutated (deep-compare before and after).
